# Ruxt 위협 모델

이 문서는 Ruxt가 **무엇으로부터 무엇을 지키는지**, 그리고 **지키지 못하는 것**이 무엇인지 적습니다. 설계 결정의 근거이자, 새 기능을 넣을 때 다시 묻는 질문 목록입니다. 구현 세부는 각 모듈(`src/core/*.rs`)의 주석을 참고하세요.

## 1. 보호 대상 (assets)

| 자산 | 위치 |
| --- | --- |
| A1. 서버 비밀번호, 키 패스프레이즈 | 메모리(인증 중, 잠금이 풀린 동안), 화면 잠금 비밀번호로 암호화한 `vault.bin` |
| A2. 개인 키 파일 | 사용자 디스크(`~/.ssh`, 사용자가 지정한 경로) |
| A3. 세션 안의 데이터 (명령, 출력, 전송 파일) | 네트워크, 메모리, 로컬 편집용 임시 파일 |
| A4. 서버 신원 (호스트 키 고정 정보) | `known_hosts` |
| A5. 로컬 PC 자체 (클립보드, 파일 시스템, 실행 권한) | — |
| A6. 설정·세션 목록 (호스트, 사용자 이름, 터널 구성) | `config.json` |
| A7. 감사 기록의 무결성 | `audit.log` |
| A8. 열려 있는 Ruxt 창 자체 (연결된 셸·SFTP·저장된 세션 목록) | 화면 |
| A9. 명령어 기록 (어떤 서버에서 무엇을 실행했는지) | `history.db`, 메모리 |

## 2. 공격자 (adversaries)

| 공격자 | 능력 |
| --- | --- |
| T1. 네트워크 중간자 | 패킷 관찰·변조, 가짜 서버로 유도 (DNS/ARP 스푸핑, 악의적 Wi-Fi) |
| T2. 악의적이거나 침해된 SSH 서버 | 프로토콜 범위 안에서 무엇이든 보냄: 터미널 이스케이프, 악성 파일명, 채널 열기 요청, X11/에이전트 포워딩 남용 |
| T3. 같은 PC의 다른 사용자 계정 | 파일 시스템 읽기(권한이 허용하는 범위), 로컬 포트 접속 |
| T4. 같은 LAN의 다른 호스트 | 터널 리스너에 접속 시도 |
| T5. 클립보드에 데이터를 넣을 수 있는 로컬 프로그램/웹 페이지 | 붙여넣기 내용 조작 (clipboard injection) |
| T6. 디스크를 통째로 얻은 공격자 (분실 노트북, 백업 유출) | 오프라인에서 모든 파일 읽기 |
| T7. 자리를 비운 사이 PC 앞에 앉은 사람 | 로그인된 세션에서 열려 있는 창을 그대로 사용 |

**범위 밖**: 같은 사용자 계정으로 실행 중인 악성 코드(프로세스 메모리 읽기, 키로깅), 커널·하드웨어 공격, 서버 쪽 데이터 유출, 사용자가 명시적으로 승인한 행동(바뀐 호스트 키 교체, 에이전트 포워딩 켜기).

## 3. 방어와 근거

### 3.1 전송 계층 (T1)

| 위협 | 방어 | 구현 |
| --- | --- | --- |
| 가짜 서버 | 호스트 키 TOFU 고정. 최초 접속은 지문+randomart를 보여주고 승인 후에만 저장. 키가 바뀌면 **연결 차단**, 사용자가 확인란을 체크하고 명시적으로 교체해야만 진행. 교체 기록 실패 시 연결하지 않음. 점프 호스트도 홉마다 따로 고정. | `hostkeys.rs`, `ssh.rs::check_server_key` |
| 다운그레이드·약한 암호 | *엄격* 프로필: KEX `mlkem768x25519-sha256`(포스트양자 하이브리드)·`curve25519-sha256`, 호스트키 Ed25519/ECDSA/RSA-SHA2, 암호 ChaCha20-Poly1305·AES-GCM, MAC ETM만. SHA-1·CBC·group1/14-sha1 없음. *호환* 프로필(DH-GEX/group14+ SHA-2, CTR 추가, SHA-1 없음)과 *레거시* 프로필(호환 + `ssh-rsa` SHA-1 호스트 키 서명)은 사용자가 세션별로 선택할 때만. DSA·3DES·RC4·CBC는 어느 프로필에도 없음(테스트로 고정). | `ssh.rs::preferred_for` |
| 수동적 복호화(미래의 양자 컴퓨터) | 포스트양자 하이브리드 KEX를 기본값으로. | 위와 같음 |
| 호스트 키 창을 띄워 놓고 타임아웃 유도 | 지문을 확인하는 동안 연결 타임아웃이 멈춤. | `ssh.rs::await_connect` |

### 3.2 자격증명 (T3, T6, 부분적으로 T2)

| 위협 | 방어 |
| --- | --- |
| 디스크의 비밀번호 유출 | 비밀은 `vault.bin`에만 저장하고 화면 잠금 비밀번호에서 Argon2id(64 MiB, 3 pass)로 유도한 키와 XChaCha20-Poly1305로 암호화, 헤더를 AAD로 묶어 변조 감지. 화면 잠금 비밀번호가 없으면 저장하지 않음(다른 기능은 모두 사용 가능). |
| 메모리 잔존 | 인증이 끝나면 세션 태스크의 비밀 사본을 즉시 소거(`zeroize`). 점프 호스트 비밀도 인증 후 소거. 유휴 시 자동 잠금(기본 15분). |
| 다른 계정의 파일 읽기 | 설정·금고·known_hosts·키·감사 로그를 생성 시점부터 0600으로 만들고 고유 임시 이름 + rename으로 원자적 저장(umask 창 없음). |
| 세션 내보내기로 비밀 유출 | JSON 내보내기에는 `SessionProfile`만 들어가며 비밀 필드가 아예 없음. |
| 서버가 키를 훔침 (에이전트 포워딩) | 기본 OFF, 켤 때 경고 표시. |
| 자리를 비운 창 사용 (T7, A8) | 앱 잠금: 처음 실행 때 비밀번호를 정하면 유휴 N분(10분 단위, 0 = 끔) 후 창 전체를 잠그고 저장된 비밀번호의 키를 메모리에서 지움. 비밀번호가 있으면 잠긴 상태로 시작. 잠금 화면에는 세션 내용이 전혀 그려지지 않고 입력도 전달되지 않음. 비밀번호는 `applock.bin`에 Argon2id(64 MiB, 3 pass) 검증값으로만 저장(상수 시간 비교), 실패마다 다음 확인이 1초씩(최대 5초) 지연. **한계**: 창 잠금 자체는 암호화가 아니므로 같은 계정으로 실행되는 코드나 디스크를 가진 공격자(T6)는 `applock.bin`을 지워 잠금을 없앨 수 있음(그래도 `vault.bin`의 비밀은 잠금 비밀번호 없이는 풀 수 없음). |
| 크래시 덤프로 메모리 유출 | 시작 시 `ruxt.exe`를 Windows 오류 보고 제외 목록(`HKCU\…\ExcludedApplications`)에 등록해 WER이 덤프를 만들거나 업로드하지 않게 함. **한계**: Linux/macOS의 코어 덤프는 OS 설정(`ulimit -c`, systemd-coredump)에 맡김. |
| 클립보드 기록·클라우드 동기화로 유출 | 설정 → 보안의 클립보드 자동 지우기: Ruxt가 복사한 텍스트가 N초 뒤에도 그대로 있으면 비움(사용자가 다른 곳에서 복사한 내용은 건드리지 않음). 기본 0(끔)이므로 사내 PC에서는 켜기를 권장. |
| 원격 편집 사본이 `%TEMP%`에서 수집됨 | 사본은 `data\edit\`(사용자 프로필, Windows 검색 인덱싱 제외)에 두고 세션·앱 종료와 크래시 뒤 청소. **한계**: 같은 계정의 EDR 샘플 제출·백업은 여전히 읽을 수 있음. |
| 세션을 켜 둔 채 자리를 비움 | 유휴 N분 뒤 모든 SSH 세션 끊기(설정, 기본 끔) + 앱 잠금. |
| 메타데이터가 영구 보관됨 (A6, A7, A9) | 명령어 기록 90일, 감사 로그 180일 기본 보관 후 시작 시 정리(0 = 영구). 감사 로그는 **기본 꺼짐**(설정 → 보안에서 켬). 감사 로그와 명령어 기록은 설정에서 끌 수 있음(감사 로그를 끄고 켜는 것 자체는 기록됨). |
| 디스크를 가진 공격자가 기록을 읽음 (T6; A6, A7, A9) | `history.db`(실행한 명령)는 줄마다 XChaCha20-Poly1305로 암호화(아래). `config.json`과 `audit.log`는 **평문**. 비밀(비밀번호·패스프레이즈·쿠키·터미널 내용)은 들어가지 않고 메타데이터(호스트, 사용자 이름, 파일 경로, 터널 목적지, Tail Viewer로 연 `tail` 명령, 시각)만 들어 있음. 소유자 전용 권한으로 다른 계정은 읽지 못함. 디스크 분실·백업 유출은 **OS 디스크 암호화(BitLocker/FileVault/LUKS)에 의존**. 같은 계정의 코드는 화면·입력·메모리를 이미 볼 수 있어 파일 암호화로 막을 수 없고, 감사 로그는 소유자가 직접 읽는 용도라 의도적으로 암호화하지 않음. |
| 명령어 기록에 비밀이 남음 (A9) | 기록 대상은 Enter 시점에 **터미널 격자에 표시된 글자**이므로 에코되지 않는 입력(비밀번호 프롬프트, `read -s`)은 저장되지 않음. 추가로 `password=`·`token=`·`Authorization:`·`*_SECRET=`·`sshpass`·`mysql -p…` 같은 패턴과 공백으로 시작하는 줄은 건너뜀(휴리스틱, 완전하지 않음). 대체 화면에서는 기록하지 않음. **화면 잠금 비밀번호가 있을 때만 기록**: `history.db`의 각 줄(명령·호스트·횟수)은 저장된 비밀번호 저장소(`vault.bin`, 잠금 비밀번호의 Argon2id 키로 암호화)에 든 무작위 키로 XChaCha20-Poly1305 암호화하고 무작위 줄 id를 AAD로 묶음. 평문으로는 줄 id와 마지막 사용 시각(보관 기간 정리용)만 남음. 잠금이 풀린 동안만 메모리에 있고 잠기면 지움. 이전 버전의 평문 테이블은 첫 잠금 해제 때 암호화 후 삭제(`secure_delete` + `VACUUM`). 잠금을 해제하면 파일을 덮어쓴 뒤 삭제. `history.db`는 0600, 설정에서 끄거나 전부 삭제 가능. **한계**: 명령행 인자로 넘긴 비밀을 패턴이 놓칠 수 있음 — 그런 명령은 앞에 공백을 두거나 기록을 끄세요. |
| 알려진 한계 | russh에 전달하는 전송용 비밀 사본 하나는 라이브러리가 소유하며 소거 시점을 Ruxt가 통제하지 못함. |

### 3.3 악의적인 서버 (T2)

| 위협 | 방어 |
| --- | --- |
| 터미널 이스케이프로 창 제목·클립보드 조작 | 창 제목·배너·KI 프롬프트에서 제어 문자와 bidi/보이지 않는 서식 문자(U+202E 등) 제거. OSC 52(원격의 클립보드 쓰기) 기본 차단. |
| 경로 탐색 (`../`, 드라이브 접두사, 예약 장치명) | 원격 파일명이 로컬 경로가 되기 전에 `safe_component`로 검증: 구분자·`..`·`C:x`·`NUL`/`COM1`·끝의 점/공백 거부. 거부된 항목은 건너뛰고 사용자에게 알림. |
| 디렉터리 심볼릭 링크로 루프·탈출 | 다운로드·삭제·복사 시 디렉터리 링크를 절대 따라가지 않음(삭제는 링크 자체만). 재귀 깊이 제한. |
| "편집" 기능으로 실행 파일 실행 | 외부 편집기가 지정되지 않으면 실행 파일·스크립트 확장자를 OS 기본 핸들러로 열지 않음. 임시 편집 파일은 종료·크래시 후 청소. |
| 서버가 임의 채널을 엶 | 요청한 원격 포워딩 포트만 수락, 그 외 서버 발신 채널 거부. X11 채널은 X11을 켠 세션에서만. 서버가 여는 채널은 세션당 64개로 제한. |
| X11로 로컬 X 서버 공격 | 서버에는 가짜 쿠키만 전달하고 Ruxt가 실제 쿠키로 교체(OpenSSH 방식). 로컬 쿠키가 없으면 인증 없는 접속을 시도하지 않고 채널 거부. Ruxt가 X 서버를 시작할 때는 무작위 MIT-MAGIC-COOKIE-1을 만들고 절대 `-ac`를 쓰지 않음. 클립보드 공유는 기본 OFF. |
| 포워딩된 X 클라이언트가 다른 창을 읽거나 키 입력을 가로챔 (X11은 같은 디스플레이의 모든 클라이언트를 서로 신뢰) | **기본 비신뢰 모드(`ssh -X`)**: 접속 시 Ruxt가 X SECURITY 확장으로 *untrusted* 트러스트 레벨의 MIT-MAGIC-COOKIE-1 인증을 발급받아 브리지가 그 쿠키로 교체. 비신뢰 클라이언트는 다른 클라이언트의 창·속성·입력에 접근할 수 없고(BadAccess), 인증은 세션 종료 시 취소. 세션 편집기의 **신뢰 모드(-Y)** 는 명시적 선택(경고 표시). SECURITY 확장이 없거나 발급에 실패하면 신뢰 모드로 조용히 내려가지 않고 X11 채널을 거부하며 이유를 표시. Cygwin 배포판의 `xorg-server`는 이 확장을 끄고 빌드되므로 `installer/fetch-xserver.ps1`이 Cygwin/X 소스(`xserver-cygwin-21.1.25-1`)를 `-Dxcsecurity=true`로 다시 빌드해 동봉하고 `MANIFEST.txt`에 기록. 인증 유효 기간은 7일(서버 타이머가 49일 이상에서 넘쳐 서버가 죽는 것을 확인). | `x11.rs::generate_untrusted`, `ssh.rs::run_session_inner`, `installer/fetch-xserver.ps1` |
| X 서버 자체의 취약점 | 동봉 X 서버는 X.org 포인트 릴리스를 가장 빨리 반영하는 Cygwin/X(`xorg-server` 21.1.x)를 쓰고, `installer/fetch-xserver.ps1`이 서명 검증된 Cygwin 설치 프로그램으로 받아 `MANIFEST.txt`에 패키지 버전과 파일 해시를 남김. 이 트리는 `ruxt.exe`에 내장되고(빌드 때 `MANIFEST.txt` 해시와 대조), 사용자가 쓸 수 있는 `%LOCALAPPDATA%\ruxt\data\xserver`에 풀리므로 **시작할 때마다** 모든 파일의 SHA-256과 `bin\`에 모르는 파일(심어 둔 DLL)이 없는지 확인하고, 다르면 새로 풂(`xbundle.rs`). IPv4 TCP만 듣고(`-nolisten inet6`, 유닉스 소켓 없음) 쿠키 없는 접속은 X 서버가 거부. **한계**: X.org에는 루프백 전용 바인드 옵션이 없어 `-listen tcp`는 TCP 6000+n을 모든 인터페이스에 엶. Windows에서는 설치 파일(관리자 설치)이 풀린 `XWin.exe`(경로는 버전이 바뀌어도 같음) 인바운드 **차단** 규칙을 넣어 LAN에서 포트를 닫고(Windows 방화벽은 루프백을 필터링하지 않으므로 Ruxt 브리지는 동작), X 메뉴가 규칙 부재를 경고하고 UAC로 추가할 수 있음. X 서버 패치는 `cargo audit`처럼 자동으로 잡히지 않으므로 릴리스 때 스크립트를 다시 실행해야 함. |
| 서버 상태 모니터 출력으로 UI 공격 | 모니터 스크립트는 읽기 전용 명령만 실행하고(`hostname`, `uname`, `/proc/*` 읽기, `df`, `who`, `ps`), 출력은 256 KiB에서 자르며 모든 숫자는 범위 검사, 모든 문자열은 제어·bidi 문자 제거 후 길이 제한. exec를 거부하거나 3회 연속 실패하면 그 세션의 모니터링을 멈춤. 기본 켬이지만 설정에서 끌 수 있음(서버 측 감사 로그에 명령 실행이 남는 환경을 위해). | `monitor.rs::parse` |
| 전송 중 끊김으로 파일 손상 | 업로드·다운로드·복사 모두 임시 이름에 쓴 뒤 원자적 교체. |

### 3.4 로컬 네트워크·로컬 사용자 (T3, T4)

| 위협 | 방어 |
| --- | --- |
| 다른 호스트가 터널을 씀 | 로컬/SOCKS 리스너는 루프백에만 바인드(설정에서 명시적으로 해제). SOCKS5는 CONNECT만, 핸드셰이크 10초 제한, 리스너당 동시 연결 256개. |
| 같은 PC의 다른 계정 | 루프백 리스너는 같은 PC의 다른 계정도 접속할 수 있음 — **알려진 한계**. 민감한 터널은 사용 후 중지. |

### 3.5 클립보드 인젝션 (T5)

| 위협 | 방어 |
| --- | --- |
| 숨은 줄바꿈으로 즉시 실행 | 여러 줄 붙여넣기 전에 확인 창(미리보기 포함). |
| ESC 시퀀스로 터미널 조작 | 붙여넣기에서 제어 문자 제거, 브래킷 페이스트 지원. |

### 3.6 감사 (A7)

접속/인증(실패 포함)/호스트 키/터널/전송/잠금/가져오기·내보내기 이벤트를 JSON Lines로 기록. 비밀은 기록하지 않음. 16 MiB 초과 시 1회 회전. 로그 파일은 0600. 로그가 기록되지 않아도 동작을 막지는 않으므로 **로컬 관리자급 공격자에게는 무결성을 보장하지 않음**.

### 3.7 코드 수준

* 바이너리 전체 `#![forbid(unsafe_code)]`. SSH는 `russh`(순수 Rust), 암호는 RustCrypto/ring, 터미널은 `alacritty_terminal`.
* 릴리스에서도 정수 오버플로 검사, LTO, 심볼 제거.
* CI: Ubuntu·Windows·macOS에서 fmt, clippy `-D warnings`, 테스트, `cargo audit`. 테스트에는 저장된 비밀번호 변조 감지, 호스트 키 교체, 파일명 검증, SOCKS5 파싱, X11 쿠키 교체, 붙여넣기 위생, 인프로세스 SSH 서버 E2E(TOFU, 변조 키 차단, 인증, 셸, 포워딩, 비요청 채널 거부), 헤드리스 UI 스모크 테스트가 포함됩니다.
* 릴리스 바이너리는 태그에서 자동 빌드되고 `SHA256SUMS`가 함께 올라갑니다. Windows 바이너리와 설치 파일은 인증서가 설정된 경우 Authenticode 서명됩니다.

## 4. 알려진 한계와 미해결 과제

1. russh가 소유하는 비밀 사본의 소거 시점.
2. 루프백 터널에 같은 PC의 다른 계정이 접속할 수 있음.
3. 호스트 인증서(`@cert-authority`)는 검증하지 않고 인증된 키 자체를 TOFU로 고정함.
4. 감사 로그는 평문이고 변조 감지가 없음. 같은 계정이나 로컬 관리자 권한 공격자는 줄을 지우거나 고칠 수 있음(해시 체인·원격 syslog 전송은 향후 과제).
5. 메모리 덤프·디버거 접근 등 같은 계정의 악성 코드는 범위 밖.
6. 그래픽 드라이버(OpenGL/wgpu)와 OS 윈도 시스템의 취약점은 Ruxt가 통제하지 못함.
7. X 서버의 TCP 포트는 X.org 설계상 모든 인터페이스에 바인드됨. Windows 방화벽 차단 규칙으로 완화(설치 파일/X 메뉴)하지만 규칙이 없는 환경과 Linux/macOS에서는 쿠키 인증만이 방어선.
8. 명령어 기록의 비밀 필터는 휴리스틱(에코 여부 + 패턴)이며 모든 경우를 잡지 못함.
9. 비밀번호·패스프레이즈를 OS 키체인(Windows Credential Manager, macOS Keychain, Secret Service)에 맡기는 대신 화면 잠금 비밀번호로 암호화하는 Ruxt 자체 저장소(Argon2id + XChaCha20-Poly1305)를 씀. 키체인 연동은 플랫폼별 의존성(DBus 등)과 "로그인만 하면 열리는" 모델의 득실 때문에 아직 채택하지 않음.
